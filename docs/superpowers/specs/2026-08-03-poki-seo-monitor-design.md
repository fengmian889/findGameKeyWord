# Poki 新游戏 SEO 机会监控系统设计

## 1. 目标

构建一个由 GitHub Actions 定时运行的自动化系统，监控 Poki 英文站的新游戏页面。系统发现新的 `/en/g/` 游戏 URL 后，抓取游戏页面，生成游戏名称词、品类与玩法词、长尾需求词，利用 Google Trends 和公开搜索信号评估美国优先、全球辅助的 SEO 机会，并通过 GitHub Issue 与仓库内结构化文件交付结果。

## 2. 成功标准

- 能从 Poki 英文 sitemap 和 New Games 页面发现新的游戏 URL。
- 同一个规范 URL 只进入一次首次研究流程，重复运行不会重复创建 Issue。
- 每个新游戏至少输出页面事实、三类候选关键词、信号证据、机会评分和建议动作。
- Google Trends 暂无数据时，不把新词直接判定为低价值，而是安排 7、14、30 天复查。
- 单个来源、单个页面或单个关键词失败时，其他任务仍可继续。
- 数据提供层可以在不修改发现与报告流程的情况下增加 DataForSEO 或 Ahrefs。

## 3. 范围

### 首期包含

- 英文站、美国市场优先。
- Sitemap 与 New Games 双通道发现。
- Google Trends、Google 自动补全和有限的公开 SERP 信号。
- 游戏名称词、品类与玩法词、长尾需求词。
- 0–100 的 Trend Opportunity Score。
- GitHub Issue、JSON、CSV、Markdown 输出。
- GitHub Actions 每日 4 次定时执行，也支持手动触发。

### 首期不包含

- 自动发布 SEO 页面或自动建站。
- 对 Poki 全站做递归爬取。
- 付费搜索量、CPC 或权威 Keyword Difficulty 数据。
- 多语言关键词研究。
- 分钟级实时监控。

## 4. 方案选择

采用 Sitemap + New Games 双通道方案。

- `https://poki.com/en/sitemaps/index.xml` 是权威发现源。
- `https://poki.com/en/new` 是提前发现与故障补偿源。
- 只接受主机为 `poki.com`、路径符合 `/en/g/<slug>`、无查询参数的规范 URL。
- 两个来源的结果先规范化再去重，避免同一个游戏重复研究。

不采用 sitemap-only，是因为 sitemap 可能存在发布延迟或临时访问失败；不采用全站爬取，是因为首期收益不足以覆盖请求量、误判和维护成本。

## 5. 系统架构

系统由以下边界清晰的模块组成：

1. **Scheduler**：GitHub Actions 定时或手动触发单次任务。
2. **Discovery**：分别读取 sitemap 索引、子 sitemap 和 New Games 页面，返回候选 URL 及来源证据。
3. **Canonicalizer**：统一协议、域名、路径与尾斜杠，移除查询参数，并验证游戏 URL 规则。
4. **State Store**：读取和更新已知 URL、首次发现时间、研究状态、复查时间和输出引用。
5. **Page Extractor**：提取标题、slug、Meta Description、正文介绍、玩法、操作、分类、标签、开发商和相关游戏。
6. **Keyword Generator**：基于页面事实生成三类候选关键词，并记录每个关键词的生成依据。
7. **Signal Providers**：通过统一接口获取 Google Trends、自动补全和公开 SERP 信号；未来增加 DataForSEO/Ahrefs 适配器。
8. **Scorer**：将原始信号标准化并计算机会分数、置信度和建议动作。
9. **Reporter**：生成单游戏 Markdown 报告、聚合 CSV/JSON，并为高价值新发现创建 GitHub Issue。

模块之间传递结构化对象，不让抓取代码直接负责评分或报告，从而保证数据源可替换。

## 6. 数据流

1. GitHub Actions 获取仓库代码和历史状态。
2. Discovery 并行请求 sitemap 与 New Games 页面。
3. Canonicalizer 过滤并去重候选 URL。
4. State Store 与历史 URL 集合比较，输出新 URL 和到期复查项。
5. 对每个新 URL 抓取并提取页面事实；无法提取关键字段的 URL 进入重试状态。
6. Keyword Generator 创建候选词，并去除纯机械、语义重复或与页面事实不符的组合。
7. Signal Providers 获取美国优先、全球辅助的趋势与搜索信号。
8. Scorer 输出分数、置信度、缺失信号和推荐动作。
9. Reporter 写入报告与结构化数据；满足 Issue 门槛时创建 Issue。
10. 只有报告和状态均成功写入后，任务才标记为已研究。

## 7. 关键词生成

### 游戏名称词

包括原始游戏名、规范化名称以及被搜索信号验证的意图修饰，例如 `play <game> online`、`<game> free`。品牌名和游戏名保持原有拼写。

### 品类与玩法词

从分类、面包屑、介绍、玩法、操作方式和相关游戏中提取主题、类型、机制、视角、人数和平台属性，再组合为自然英文短语。组合必须能追溯到页面事实。

### 长尾需求词

围绕玩法、操作、替代品和访问意图生成候选词，例如 `how to play <game>`、`<game> controls`、`games like <game>`、`<game> unblocked`。候选词只有在自动补全、相关查询、趋势或 SERP 意图提供支持时才进入推荐列表；否则保留为未验证候选。

## 8. 信号与评分

免费版不声称提供绝对搜索量或权威关键词难度。最终指标命名为 `Trend Opportunity Score`。

| 信号 | 权重 | 内容 |
|---|---:|---|
| 趋势强度与增速 | 30 | 美国近 7、30、90 天趋势，全球趋势作为辅助，关注上升和 breakout 查询 |
| 新鲜度 | 25 | 首次发现时间、New Games 页面位置、两个来源的发现时间差 |
| 竞争缺口 | 20 | 搜索结果中精准匹配页面、强势游戏站和内容覆盖情况 |
| 搜索意图匹配 | 15 | 自动补全、相关查询和 SERP 页面类型是否支持候选意图 |
| 长尾扩展潜力 | 10 | 经验证且不重复的品类词和需求词数量与质量 |

结果分级：

- 75–100：立即调研并进入内容生产评估。
- 55–74：重点观察。
- 35–54：保留并等待趋势变化。
- 0–34：暂不投入。

评分同时输出 `confidence`。当 Trends、自动补全或 SERP 信号缺失时，降低置信度而不是虚构数值。对完全没有趋势数据的新词安排 7、14、30 天复查。

## 9. 状态与输出

建议目录结构：

```text
data/
  state.json
  games.jsonl
  keywords.csv
reports/
  YYYY-MM-DD/<game-slug>.md
```

`state.json` 保存 URL 级状态和调度信息；`games.jsonl` 保存每次研究结果的不可变记录；`keywords.csv` 提供便于筛选和导入表格的关键词级视图；Markdown 保存适合人工审阅的完整证据。

每个游戏记录至少包含：规范 URL、来源、首次发现时间、页面字段、关键词、原始信号、评分、置信度、建议动作、错误信息、复查时间和 GitHub Issue 编号。

默认只有分数不低于 55，或因趋势缺失进入复查队列的新游戏创建 Issue。一次运行发现多个普通机会时合并为一个摘要 Issue，避免通知泛滥；分数不低于 75 的机会单独创建高优先级 Issue。

## 10. 幂等性与并发

- 规范 URL 是游戏主键。
- GitHub Actions 使用并发组，后一次计划任务不会与前一次同时修改状态。
- Issue 带稳定标识，例如规范 URL 的哈希；创建前检查已有输出引用。
- 状态文件采用读取、生成完整新版本、原子替换的方式更新。
- 报告成功而 Issue 创建失败时保留待通知状态，下次只补 Issue，不重复研究。

## 11. 异常处理

- Sitemap 失败：继续使用 New Games，并把运行状态标记为 degraded。
- New Games 失败：继续使用 sitemap。
- 两个发现源都失败：不修改已知 URL 集合，任务失败并保留诊断日志。
- 页面抓取失败：指数退避重试；达到单次上限后记录下次重试时间。
- 页面结构变化：关键字段校验失败并保留原始诊断片段，不能产出看似正常的空报告。
- Google Trends 限流或无数据：降低置信度、安排复查，不阻塞其他游戏。
- GitHub Issue 创建失败：结构化报告仍保存，并在下一次执行补发。
- 单次运行设置最大新游戏数和请求预算，剩余项目排队到下次执行。

所有外部请求使用明确的 User-Agent、超时、重试上限和低并发，遵守公开访问规则，不绕过登录、验证码或访问控制。

## 12. GitHub Actions 行为

- 使用 cron 每 6 小时运行一次，并提供 `workflow_dispatch`。
- 使用最小权限；只有写数据分支和创建 Issue 时授予对应权限。
- 使用并发组防止任务重叠。
- 若无新游戏且无复查项，不产生数据提交或 Issue。
- 数据有变化时，由工作流提交本次状态与报告；提交信息包含运行日期和新增游戏数量。
- 密钥全部存放在 GitHub Actions Secrets，未来接入付费 API 时不改数据文件格式。

## 13. 测试与验收

### 单元测试

- sitemap 索引、URL sitemap、命名空间和压缩 sitemap 解析。
- New Games 页面链接提取。
- URL 规范化、过滤和去重。
- 页面字段提取和结构变化检测。
- 三类关键词生成与语义去重。
- 各评分分量、缺失数据和边界分数。
- 状态迁移、复查调度和 Issue 幂等键。

### 集成测试

- 使用固定 HTML/XML 样本完成发现到报告的完整流程，不依赖实时网络。
- 模拟一个来源失败、Trends 限流、Issue 失败和中途重跑。
- 验证重复输入不会产生重复游戏记录或 Issue。

### 上线验收

- 首次运行建立基线，不把全部历史游戏当作新游戏创建 Issue。
- 人工注入一个未见 URL 后，仅产生一份研究记录。
- 连续运行两次，第二次无重复输出。
- 任一发现源失败时，另一个来源仍能完成发现。
- 报告明确区分事实、候选词、已验证信号和推断。

## 14. 首次运行策略

第一次运行只建立当前 URL 基线，并从 New Games 页面最前面的少量游戏中选择样本进行研究，用于验证提取与评分质量。它不会为 sitemap 中全部历史游戏批量创建 Issue。基线完成后，后续新 URL 才进入标准通知流程。

## 15. 后续扩展

增加 DataForSEO 或 Ahrefs 时，实现新的 Signal Provider，并把绝对搜索量、CPC、关键词难度、SERP 特征和竞争域指标加入原始信号。现有发现、状态、报告和 Issue 流程保持不变；评分模型通过版本号区分免费版与付费版结果，避免历史分数不可解释。
